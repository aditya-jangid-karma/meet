Setting Up an n8n Workflow to Read Invoice PDFs and Extract Vendor + Invoice Info

A step-by-step, plain-English setup guide for Team D (Puneet, Dhruv, Manish, Vijayesh)

Written: 2026-07-27  |  For: monthly close automation  |  Level: no coding background required

What this workflow does: You point it at a folder of invoice PDFs (the kind you already have — utility bills, supply invoices, vendor bills). It automatically opens each PDF, figures out where one invoice ends and the next begins, works out who the vendor is (the company that sent the invoice, not the property being billed), pulls out the invoice number, date, and amount, and writes one summary row per invoice into a spreadsheet (like your predictions.xlsx file) — without anyone retyping anything by hand.

This guide documents two different ways to build it inside a tool called n8n (pronounced "n-eight-n"). Path A reads the text that is already hidden inside your PDFs and hands that text to an AI model to interpret. Path B skips the text-reading step and instead shows a picture of each page to a "vision" AI model that can read and understand images directly. Both paths end with the same result: a clean row per invoice in your spreadsheet.

1. What you'll need (prerequisites)

Before touching either path, get these four things set up. Everything below is free and runs on a normal Windows laptop (a GPU helps speed things up but is not required to get started).

1.1 n8n — the workflow builder itself

n8n is the app you'll build the automation in. Think of it like a flowchart builder: you drag boxes ("nodes") onto a canvas, connect them with arrows, and each box does one job (read a file, ask an AI a question, write a spreadsheet row). "Self-hosted" means it runs on your own computer/server instead of a paid cloud service — important for privacy, since invoice data never has to leave your machine.

Pick one of these two ways to run it:

OptionWhat to install / typeWhy you'd choose it
Docker Desktop (recommended) 1. Install Docker Desktop for Windows from docker.com and open it once so it's running.
2. Open PowerShell and run: 
docker run -it --rm --name n8n -p 5678:5678 -v n8n_data:/home/node/.n8n docker.n8n.io/n8nio/n8n
3. Open a browser to http://localhost:5678 		Keeps n8n cleanly boxed off ("containerized") from the rest of Windows. Easiest to update or remove later. Best choice if you'll keep this running long-term.

Either way, "self-hosted" is what keeps this private — your PDFs and the text/images inside them stay on your own PC and are never uploaded to n8n's company or anyone else's cloud service.

1.2 Ollama — for running an AI model locally, for free, privately

Ollama is a small free program that lets you download and run AI language models directly on your own computer, instead of calling out to a paid service like ChatGPT. This is the key to keeping client financial data private.

  1. Download and install Ollama from ollama.com (Windows installer, click-through, no special settings needed).
  2. Open PowerShell and download ("pull") a model. For Path A (text only), a good general-purpose starting model is: 
    ollama pull llama3.1:8b
  3. For Path B (vision/images), pull a vision-capable model instead, for example: 
    ollama pull llama3.2-vision
  4. Leave Ollama running in the background (it starts automatically after install and listens on http://localhost:11434). n8n will talk to it at that address.
Hardware note: An 8-billion-parameter model like llama3.1:8b runs comfortably on most modern laptops (16 GB RAM is plenty). Vision models are bigger and slower on a laptop without a dedicated GPU — see the comparison table below.

1.3 A place to write the output — Google Sheets or Microsoft Excel

  • Google Sheets: Free Google account, a spreadsheet created ahead of time with column headers (e.g., File, Vendor, Invoice Number, Invoice Date, Amount). n8n connects via a Google "credential" (see glossary) that you set up once.
  • Microsoft Excel: You can keep using your existing predictions.xlsx file. n8n's Microsoft Excel node can connect to Excel Online (OneDrive/SharePoint) via a Microsoft credential, or you can use a local "Read/Write Files from Disk" + a Code node to append rows to a local .xlsx file.

1.4 The folder of invoice PDFs

Have a folder ready on your computer, for example C:\Users\Puneet\Desktop\invoices\, with the PDFs you want processed. This is the folder n8n will "watch" or read from.

Prerequisites checklist

  • n8n installed and reachable in a browser (Docker Desktop or npx n8n)
  • Ollama installed and running (http://localhost:11434)
  • At least one text model pulled (e.g. llama3.1:8b) for Path A
  • At least one vision model pulled (e.g. llama3.2-vision) for Path B — only needed if you're building Path B
  • A Google Sheet or Excel file ready to receive rows, with column headers already typed in
  • A folder of invoice PDFs to test against

2. Glossary — key terms explained

n8n
The workflow-automation app this whole guide is about. You build automations visually by connecting "nodes" on a canvas.
Node
One box/step in an n8n workflow. Each node does one specific job — e.g., "read a file," "call an AI model," "add a row to a spreadsheet." You connect nodes in order with arrows to build the full process.
Trigger
The special first node that starts the workflow. It answers the question "when should this run?" — e.g., "whenever a new PDF appears in this folder" or "whenever I click a Test button."
Credential
A saved, securely-stored login/connection (like your Google account or Microsoft account) that n8n reuses so you don't have to log in every time a workflow runs. n8n stores these encrypted; you set them up once per account.
Ollama
Free software that runs AI language models directly on your own computer (instead of over the internet). This is what makes a fully private, local setup possible.
Model
The actual AI "brain" that reads text or images and produces an answer. Different models trade off speed, accuracy, and size (e.g., llama3.1:8b is smaller/faster, others are bigger/smarter but slower).
LLM (Large Language Model)
The general category of AI model used here — trained on huge amounts of text so it can read a document and answer questions about it in plain language, or return structured data like JSON.
Vision model
A special kind of LLM that can look at an image (like a photo of an invoice page) and understand both the picture and any text in it at the same time, without a separate text-extraction step.
JSON
("JavaScript Object Notation") — a simple, structured way to write data as labeled fields, e.g. {"vendor": "Staples", "amount": 214.50}. We ask the AI model to answer in this format so n8n can read the fields reliably instead of parsing loose sentences.
OCR (Optical Character Recognition)
Software that looks at a picture of text (like a scanned or photographed page) and converts it into actual, selectable/searchable text. Only needed when a PDF is an image of a document rather than a "real" digital document with embedded text.
Digital PDF vs. scanned PDF
A digital PDF was created directly from a computer document (e.g., exported from an accounting system) and already contains real, selectable text you can highlight and copy. A scanned PDF is essentially a photograph of a paper page — it looks like text but is really just an image, so a computer can't read it directly without OCR. Most of Team D's invoices are digital PDFs already, which is why Path A usually works without any OCR at all.
Docker
A tool that runs an application (like n8n) in a self-contained "box" (called a container) so it doesn't clutter or conflict with the rest of your Windows setup, and can be easily started, stopped, or removed.

3. Path A vs. Path B — comparison table

Both paths produce the same output (a row per invoice with vendor, invoice number, date, amount). They differ in how they get there.

Factor Path A — Text → LLM (two-stage) Path B — Vision LLM (one-stage)
How it works Pulls the real, embedded text out of the PDF first (or OCRs it if scanned), then sends that text to a language model to interpret. Converts each page to an image and sends the picture directly to a vision-capable model, which reads and interprets in one step.
Accuracy on your PDFs today Very high — your invoices are almost all digital PDFs with clean embedded text, so extraction is exact (no guessing). Good to very high, but reading text out of an image is inherently a little less certain than reading real embedded text — the model is "eyeballing" characters.
Speed Fast. Reading embedded text is close to instant; the text model only has to read a page or two of plain text. Slower. Converting pages to images and running a vision model takes noticeably more time and computing power per page.
Hardware needed (local) Light. A normal laptop handles an 8B text model comfortably. Heavier. Vision models are larger; without a decent GPU, expect slow responses (many seconds to a minute+ per page).
Works on scanned / photographed invoices? Only with an added OCR step (extra node) — otherwise there's no text to read. Yes, natively — this is the main advantage of Path B. The model reads the image regardless of whether it's a "real" digital PDF or a scan.
Complexity to build A bit more plumbing (extraction node + OCR fallback branch), but each piece is simple and predictable. Fewer nodes overall (one AI step does the reading and understanding), but each node is heavier and slower to run/test.
Best when… Your PDFs already contain real text (this is Team D's situation today) and you want speed + low hardware needs. You start receiving scanned/photographed invoices, or you want a single simpler-looking pipeline and don't mind the extra runtime/hardware cost.

PATH A
OCR / Text → LLM (two-stage)

Path A has two AI-adjacent stages: first pull out the real text from the PDF (fast, free, no AI needed for digital PDFs), then hand that plain text to a language model to interpret it into structured fields. Below is every node you'll add, in order, left to right on the n8n canvas.

A-5. Parse and validate the JSON

Node: "Parse & Validate JSON"
Type: Code node (JavaScript) — or a simpler Set node if your n8n version auto-parses the LLM output

Purpose: Safety net. The LLM should return clean JSON, but occasionally it adds stray words or gets a field wrong. This node checks the JSON is valid and that required fields (vendor, amount) aren't empty, and flags anything suspicious instead of silently writing a bad row.

Example Code node content
const raw = $input.item.json.text || $input.item.json.output;
let data;
try {
  data = JSON.parse(raw);
} catch (e) {
  return [{ json: { error: "Could not parse JSON from model", raw } }];
}

if (!data.vendor || data.amount === undefined) {
  data._flag = "Missing vendor or amount — needs manual review";
}

return [{ json: data }];

PATH B
Straight to the LLM (vision) — one-stage

Path B skips separately extracting text. Instead, each invoice page is turned into an image, and a vision model looks at the picture directly — reading the text and understanding the layout (logos, "remit to" boxes, tables) in one step, the same way a person would glance at the page.

B-1. Trigger node(s)

Node: "When clicking 'Test workflow'" + "Watch Invoice Folder"
Type: Manual Trigger and Local File Trigger

Purpose: Identical to Path A step A-1 — one trigger for manual testing, one for automatically picking up new PDFs dropped into your invoices folder. Configure exactly the same way (see A-1 above).

B-2. Read the PDF and convert pages to images

Node: "Read Invoice File"
Type: Read/Write Files from Disk

Purpose: Same as A-2 — loads the PDF file as binary data. Configure the same way.

Node: "Convert PDF Pages to Images"
Type: Execute Command

Purpose: Most vision models expect an image (like a PNG or JPG), not a raw PDF file. This node turns each page of the PDF into its own image file so the vision model can "look" at it.

SettingWhat to enter
Command (using Poppler's pdftoppm)pdftoppm -png -r 200 {{ $json.path }} {{ $json.path }}_page
AlternativeA small Python script using the PyMuPDF library run via Execute Command can do the same conversion with more control over image size/quality.

Note: this step is only needed if your chosen vision model requires images. Some newer model/n8n integrations can accept a PDF file directly — check your model's documentation; if it accepts PDFs natively, you can skip straight from B-2's file-read to the vision node in B-3.

Node: "Read Image File"
Type: Read/Write Files from Disk

Purpose: Loads each generated page image back into the workflow as binary data so it can be attached to the vision model call.

SettingWhat to enter

4. Which should Team D pick?

Recommendation: start with Path A. Nearly all of your invoice PDFs today are digital files that already contain real, selectable text — the vendor-extraction test already proved a local model reads these correctly, including vendors identified only by a logo at the top of the page (something the old rule-based script missed). Path A takes advantage of that: it's faster, needs less computing power, and keeps everything private on a modest laptop with a small local model. There's no reason to pay the extra time/hardware cost of a vision model for documents that already have clean text sitting inside them.

Keep Path B in your back pocket for two situations: (1) if you start regularly receiving scanned or photographed invoices (faxes, phone-camera photos, old paper files) where there's no embedded text to extract at all, or (2) if, down the road, you'd rather maintain a single simpler-looking pipeline and are willing to accept slower runs and heavier hardware needs (ideally a machine with a GPU) in exchange for one less moving part. For now, given your PDFs, your privacy requirements, and your existing hardware, Path A is the practical default.

5. Testing & verification tips

  • Start small. Point the workflow at a folder with just 2-3 known invoices first (e.g., one Staples, one Quill, one Chadwell Supply) so you can check the output by eye before running it against everything.
  • Use "Execute Node" per step. In n8n, you can run one node at a time and inspect its output on the right-hand panel before moving to the next node — this is the best way to catch a problem early instead of debugging the whole chain at once.
  • Compare against a known-good list. Keep a small reference sheet of "PDF file name → correct vendor" for a handful of invoices you've already checked by hand, and compare the automation's output against it each time you change the prompt or swap models.
  • Watch for duplicate files. Some invoices get saved twice under slightly different file names (e.g., a "- Copy" version). The workflow will happily process both as separate rows — that's expected; just be aware when reconciling totals.
  • Re-test after any prompt change. Even a small wording tweak in the prompt can change how the model reads an invoice — re-run your small test batch every time you edit the prompt.
  • Log the raw model reply somewhere for the first few weeks. Add a temporary column in the spreadsheet (or a separate "raw output" node) that stores the model's original JSON text, so if a row looks wrong later, you can see exactly what the model said and why.

6. Troubleshooting mini-FAQ

The model is really slow — a single invoice takes forever.

Try a smaller model first (e.g., drop from an 8B model to a 3B model with ollama pull llama3.2:3b) — smaller models respond much faster with only a modest accuracy trade-off for straightforward invoices. If you're on Path B (vision), slowness is expected on a laptop without a GPU; consider adding a GPU, using a smaller vision model, or shrinking the page image resolution in the "Convert PDF Pages to Images" step (e.g., lower the -r value from 200 to 150).

The JSON came back malformed / n8n can't parse it.

Tighten the prompt: explicitly say "respond with ONLY valid JSON, no extra commentary, no markdown code fences" and give the exact field names and shape (as in the example prompts above). If your n8n version supports it, turn on "Require Specific Output Format" or attach a JSON Output Parser node to the LLM chain, which forces a valid structure. Also make sure the Parse & Validate JSON node (A-5 / B-4) is in place — it catches and flags bad replies instead of letting them silently break the spreadsheet write step.

The vendor looks wrong — it seems to have picked the property/customer instead.

This is the classic "vendor vs. billed-to" mix-up. Remind the model explicitly in the prompt: "the vendor is who ISSUED the invoice (the seller), not who is being billed (the customer/property)." The example prompts above already include this instruction — if you've customized the prompt, double check that line is still there. It also helps to give the model 2-3 concrete example vendor names it might see (as in the prompts above) so it has a clearer sense of what a "vendor" name looks like on your documents.

How do I know if a PDF is "digital" or "scanned"?

Open the PDF and try to click-and-drag to highlight some text. If you can select and copy real text, it's a digital PDF and Path A's plain text-extraction step will work directly. If clicking just selects the whole page like a picture (no individual letters highlight), it's a scanned/image PDF and needs the OCR fallback (Path A) or a vision model (Path B).

Some invoices span multiple pages — how does the workflow know where one invoice ends and the next begins?

This is what the is_new_invoice field in the JSON is for. Process pages in order, and each time the model says is_new_invoice: true, treat that as the start of a new invoice group; pages that come after with is_new_invoice: false belong to the same invoice as the one before them. If you notice the model splitting a single multi-page invoice incorrectly, add a note to the prompt: "a continuation page usually repeats the same invoice number or vendor name as the page before it — treat those as the same invoice."

Do I need Docker AND npx n8n?

No — pick one. Docker Desktop is the sturdier long-term choice if you'll run this workflow regularly (e.g., every month at close). npx n8n is fine for a quick first look or for testing on a machine where you don't want to install Docker.
